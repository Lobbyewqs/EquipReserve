# 事务设计复盘（本地实现，不是线上事故）

## 2026-10-19：MySQL 实现

当前主库为 MySQL 8.4.9 / InnoDB，SQLite 作为兼容后端保留。MySQL 事务在 READ COMMITTED 下先竞争幂等记录唯一键，再用 SELECT FOR UPDATE 获取设备行和预约行；预约的 device_id 不可变，因此先查询其设备 ID，再按设备→预约顺序锁定。过期任务使用相同顺序。同设备请求串行，不同设备不共享全库写锁。

幂等占位与成功结果在同一事务内提交，失败回滚移除占位。重复键插入等待前次事务完成后读取结果，不依赖全局进程锁。借出唯一约束以生成列和唯一索引替代 SQLite 部分索引。迁移脚本先导入设备空借用指针，再导入预约，最后恢复 current_loan_id，全程保留外键校验。

真实 MySQL 测试覆盖并发竞争、幂等重放、业务回滚、领取/过期边界、不同设备独立写入、密码重置和旧数据迁移。未做生产负载、死锁自动重试或掉电恢复验收。以下为 SQLite 初版设计记录。

## 不变量

slot_occupancy 的 (device_id, slot_start) 主键阻止重复占用；reservation 保留历史。取消与过期通过 reservation_id 删除占用，旧请求不会误删新预约。BORROWED 的部分唯一索引进一步保证同设备至多一笔借出；current_loan_id 与状态在同一事务提交。

SQLite 无设备级 SELECT FOR UPDATE。本版在读取幂等记录之前执行 BEGIN IMMEDIATE，取得数据库写锁后读取和修改全部相关记录。竞争者等待写锁释放，再看到提交后的幂等记录或占用。代价是不同设备也不能并行写，不能把这一实现描述成原计划的设备级串行化。

## 故障与幂等

成功结果与业务数据一起提交。创建占用后注入 RuntimeError，测试直接验证四张相关表没有部分结果。业务冲突先回滚，再单独写失败审计，不留下“处理中”的幂等占位。

请求摘要包含操作目标和规范化 JSON；预约时间统一为 UTC。历史成功重放返回原成功结果，不代表资源当前状态，例如后来已取消的预约重放创建仍返回原创建结果；客户端应查询预约列表获取现状。

## 边界

领取为 slot_start <= now < pickup_deadline；过期为 now >= pickup_deadline；取消为 now < slot_start。三条路径在事务内再次读状态和时间。提前归还不删除占用，防止同一时段反复借还。旧 RETURNED 请求只返回原状态，不修改设备指针。

## 下一阶段

迁移 MySQL 时，需要按计划建立幂等记录→设备→预约→占用的锁顺序，并处理唯一键竞争后新事务重读、死锁与锁等待超时；不能把本次 SQLite 测试结果当作 MySQL 的正确性证明。生产故障注入应增加强制进程终止及持久化恢复场景。
